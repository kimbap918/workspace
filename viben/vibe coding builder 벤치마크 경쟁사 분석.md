# vibe coding builder 벤치마크 경쟁사 분석

본 보고서는 Vibench(`https://vibench.vibe-x.app/`)과 유사하게 **Lovable·Replit·Manus·v0·Bolt 등 “E2E vibe-coding builder(프롬프트→배포된 앱)” 자체를 벤치마킹**하는 공개 플랫폼이 존재하는지 조사 및 분석한 보고서입니다.

<br>

## 0. 결론
 
### 직접 경쟁은 존재한다

 특히 App-Bench 및 UI-Bench, 그리고 DesignArena는 **‘빌더/에이전트’를 모델이 아니라 “완성된 결과물” 중심으로 비교·랭킹**한다는 점에서 Vibench와 같은 문제를 정면으로 다루고 있습니다.

<br>

### Vibench의 차별점
 (a) 기능성(통과/실패) 중심(App-Bench), (b) 시각적 선호(UI-Bench), (c) 대규모 커뮤니티 선호·토너먼트 기반(DesignArena)으로 각각 강점이 있으나, **로컬라이제이션·멀티모달 자산·브랜드 준비도·프롬프트와 재현성 및 커뮤니티**를 한 플랫폼에 묶어 제공하는 공개 벤치마크는 아직 희소합니다.


<br>

## 1. 경쟁사


### App-Bench
![Image](https://github.com/user-attachments/assets/7108de08-3416-44b3-be68-c726726d8b25)
**정체성 및 포지션**: 프롬프트 하나로 생성된 “실제 웹앱”을 기능 루브릭으로 채점해, 빌더/코딩 에이전트를 함께 비교하는 공개 벤치마크. “One-shot generation, zero human edits” 라는 표어를 내걸고 있습니다.

### UI-Bench
![Image](https://github.com/user-attachments/assets/18291eac-9485-4e4d-a529-61d0e6defc3f)

| 항목          | 내용                                                                            |

| 제품명         | UI-Bench                                                                      |

## 2. Vibench 대비 경쟁사 비교 분석

### 경쟁사 대비 핵심 차이 요약

- **App-Bench**는 기능성에 매우 강하다. 루브릭 기반 0/1 채점, 2인 개발자 수동검증, Docker/Next.js 템플릿 등으로 “정답에 가까운 기능”을 본다. 반면 UI/브랜드/로컬라이제이션 같은 제품화 신호는 의도적으로 비중이 낮다. 
- **UI-Bench**는 “시각적 완성도”에 특화되어, 기능보다 ‘클라이언트에 납품할 만한가’라는 디자인/브랜딩 신호를 가장 강하게 제공한다. 반면 실제 기능·백엔드·보안·운영성은 범위 밖이다.  
- **DesignArena**는 커뮤니티 기반으로 스케일을 확보한다. 블라인드 토너먼트 + Bradley–Terry/Elo로 “사람이 실제로 더 좋아하는 결과”를 빠르게 축적하며, 최근에는 풀스택 검증을 하이브리드로 확장하고 있다. 하지만 ‘정확한 재현’과 ‘정답지 기반 기능 커버리지’는 App-Bench만큼 명시적이지 않다. 

<br>

| 재현성       | 입력 아티팩트 제한(라이브 URL/ZIP/스크린샷/시간) (내부) | Docker/템플릿 등 조건 명시, 프롬프트·루브릭 공개 | 프롬프트 공개, 프로토콜 공개              | 방법론·시스템 프롬프트 공개(일부), 대규모 사용자 투표에 의존 |
| 확장성       | LLM 증거 기반 판별의 신뢰성 확보 필요              | 평가자 수동부담이 병목                    | 전문가 모집/운영이 병목                 | 커뮤니티 규모가 확장성의 핵심                    |
| CI/API 통합 | 공식 API/CI는 확인 불가                     | 공식 API/CI는 확인 불가                | 공식 API/CI는 확인 불가              | API 언급은 있으나 공식 문서로 확인 불가            |

| 약점        | 외부 검증 가능한 공개 데이터/루브릭 확장이 과제          | UI/브랜드/로컬은 비중 낮음                | 기능/백엔드/보안 범위 밖                | 재현성·세부 루브릭 투명도가 상대적으로 약할 수 있음       |

### PS. 벤치마크 상위권 빌더에 대한 의문
<img width="1236" height="888" alt="image" src="https://github.com/user-attachments/assets/fbf8b2f5-f6bb-4940-9c46-3945a9799259" />

UI-Bench와 App-Bench 리더보드에서 **Orchids**(https://www.orchids.app/)와 같은 신생 빌더가 Claude Code를 이기며 동시에 최상위권에 위치하고 있습니다. 특히 두 벤치마크가 동일 계열 운영 주체(AfterQuery)와 연관되어 있다는 점에서, 다음과 같은 의문이 제기됩니다.

- 특정 벤치마크 태스크에 대한 과적합 가능성
- 동일한 공개 루브릭·프롬프트 환경에 대한 사전 최적화 가능성
- 해당 Orchids 빌더가 App-Bench에 의해 바이럴 되고있을 가능성

    

다만, 현재 공개 정보만으로 운영 구조상 이해관계 또는 의도적 조작을 단정할 근거는 확인되지 않습니다. 빌더가 모델 단독 성능이 아닌 **템플릿·에이전트 파이프라인·워크플로우 설계 최적화**를 통해 특정 태스크에서 높은 점수를 얻는 구조적 가능성도 존재합니다.
