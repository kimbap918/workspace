## 1. 핵심 평가 원칙

Viben의 채점 시스템은 주관적 해석을 배제하고 객관적 지표를 확보하기 위해 다음 4가지 원칙을 준수

1. **입력 데이터 제한:** 평가 근거는 오직 **(1) Live URL(또는 스크린샷), (2) Code ZIP(프로젝트 루트), (3) Generation Time**만 사용
    
2. **증거 기반 채점:** 모든 세부 항목의 점수는 반드시 **2개 이상의 구체적 증거(파일 경로, 특정 화면 섹션 등)**가 뒷받침되어야 함
    
3. **합리적 추론:** 코드 파일이 일부 잘렸더라도 `import` 구문이나 폴더 구조를 통해 해당 기능의 존재를 합리적으로 추론할 수 있다면 점수를 인정
    
4. **이상치 제어:** 편차가 큰 항목(Multimodal, Self-healing 등)은 가중치를 낮게 설정하며, Iteration 모드에서는 Trimmed Mean(최고/최저 제외 평균)을 적용하여 변동성을 최소화
    

### 평가 방법
공정성을 보장하기 위해 다음과 같은 4단계 파이프라인을 거쳐 최종 점수 확정

1. **Code Digest:** 프로젝트 ZIP 파일을 분석하여 파일 구조, 주요 코드, 프레임워크 시그널을 요약
2. **Gemini Analysis:** System Prompt와 스코어링 기준을 탑재한 Gemini 모델이 증거를 기반으로 JSON 형태의 채점표를 생성
3. **Validation & Calculation:** 파이썬 스크립트가 JSON을 파싱하여 수학적 정합성을 검증하고, 가중치 공식을 적용하여 점수를 계산
4. **Iteration:** 편차를 줄이기 위해 Temperature 0.2 환경에서 N회 채점을 수행하고, 극단값(Outlier)을 제거한 후 최종 평균을 산출

<br>

## 2. 스코어링 산정 공식

총점은 3가지 주요 섹터의 가중 평균 합산으로 산출되며, 정수 단위(Integer Only)의 LLM 채점 결과를 정밀한 수학적 모델로 계산

### 1) 기본 원칙
- 모든 세부 항목은 **1~5점**으로 평가

> - **1점 (Critical Failure):** 실행이 불가능하거나, 요구사항과 전혀 다른 결과물
> - **2점 (Below Standard):** 실행은 되지만 로직이 오작동하거나, UI가 심각하게 깨진 상태
> - **3점 (Base Standard):** 핵심 기능이 정상 동작하며 에러가 없는 상태
> - **4점 (Generous Good):** 3점을 충족하고, UX가 매끄럽거나 코드가 깔끔한 경우
> - **5점 (Strict Perfect):** 단순 구현을 넘어 전문가 수준의 디테일이 증명된 경우
> - **Note:** 모든 점수는 **Evidence(증거)**가 없으면 인정되지 않으며, 증거 확보가 불가능한 경우 보수적으로 채점하거나 '미확인' 처리

$$\textbf{Total Score} = (A_w \times 12) + (B_w \times 6) + (C_w \times 2)$$
- $Aw$: Core Performance 가중평균(0~5)
- $Bw$: Developer Experience & Efficiency 가중평균(0~5)
- $Cw$: Brand Readiness 가중평균(0~5)

<br>

### 2) 평가 섹터 상세 

* 각 섹터 점수($A_w, B_w, C_w$)는 세부 항목의 중요도에 따른 가중 평균으로 계산

<br>

#### **A. Core Performance (핵심 성능 - 60%)**

> **목적:** 사용자의 의도를 “작동하는 앱”으로 구현하는 능력

$$A_w = 0.12 \text{Context} + 0.05 \text{MultiModal} + 0.10 \text{Local} + 0.28 \text{Logic} + 0.20 \text{Layout} + 0.25 \text{Depth}$$

<br>

#### **B. Developer Experience (개발 및 운영 효율 - 30%)**

> **목적:** 생성 속도/운영 효율/비용 대비 산출물 완성도

$$B_w = 0.40 \text{Quality} + 0.40 \text{Efficiency} + 0.12 \text{Cost} + 0.08 \text{SelfHealing}$$

<br>

#### **C. Brand Readiness (브랜드 준비도 - 10%)**

> **목적:** 일관된 디자인 시스템과 브랜드 아이덴티티를 갖췄는가?

$$C_w = 0.40 \text{Identity} + 0.35 \text{Consistency} + 0.25 \text{Assets}$$
<br>

## 3. 항목별 상세 평가 기준

모든 항목은 **1~5점 척도**로 평가되며, 1점(Failure), 2점(Below), 3점(Base), 4점(Good), 5점(Perfect)의 명확한 앵커(Anchor) 기준을 따름


#### PDL(Prompt Difficulty Level) 판정 (L1/L2/L3)

채점 시작 전에 사용자의 입력 프롬프트를 아래 기준으로 **L1/L2/L3 중 하나로 분류**
PDL은 **A-4 Logic**, **B-1 CodeQuality**, **B-2 GenEfficiency** 평가 기준에 반영
- **L1 — Landing/소개형**
    - 키워드 예: introduce, showcase, landing, portfolio, just introduce
    - 결과 기대: 섹션 구성/내비/탭·필터/제품 상세(모달·섹션) 중심 소개 경험  
- **L2 — App/CRUD형**
    - 키워드 예: dashboard, admin, CRUD, save/edit/delete, database, API, search+filter+sort
    - 결과 기대: 데이터 생성·수정·삭제, 폼 검증, 상태관리, 에러 처리  
- **L3 — Service/E2E형**
    - 키워드 예: auth/login, role/permission, payment/checkout, booking, subscription, onboarding
    - 결과 기대: 인증·권한·결제/완료 상태 포함한 다단계 워크플로우
