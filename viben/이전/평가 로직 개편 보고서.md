# Viben Generation Efficiency 평가 로직 개편 및 고도화 보고서

## 1. 개편 배경: AI 코딩 툴의 템플릿(Boilerplate) 활용 트렌드 분석

초기 Viben 시스템의 효율성(Efficiency) 평가는 프로젝트의 '전체 파일 수'나 '전체 코드 길이'를 기준으로 산정되었습니다. 그러나 최근 자사(VibeX)를 포함하여 Lovable, v0, Bolt 등 주요 AI 코딩 툴들의 생성 결과물을 분석한 결과, **개발 초기 세팅을 돕기 위해 다수의 공통 템플릿 파일과 설정 파일을 일괄 생성하는 트렌드**가 공통적으로 확인되었습니다.

**[주요 AI 툴별 공통 파일(Boilerplate) 생성 현황]**

- **VibeX & Lovable:** 초기 환경 구축 시 세련된 UI를 제공하기 위해 `shadcn/ui` 기반의 범용 컴포넌트(`accordion.jsx`, `button.tsx` 등)를 다수 생성합니다. VibeX는 생성된 99개의 공통 파일 중 84개가, Lovable은 83개 중 73개가 내용이 변하지 않는 기본 템플릿 파일이었습니다.
    
- **v0 & Manus:** Next.js 기반의 환경 설정을 위해 `next-env.d.ts`, `components.json`, 정적 에셋 등을 기본 생성하며, 각각 18개(총 24개 중), 21개(총 27개 중)의 동일한 공통 파일을 활용합니다.
    
- **Bolt & Replit:** 프로젝트 빌드 및 환경 설정을 돕기 위해 `.bolt/config.json`, `package-lock.json`, `vite.config.ts` 등의 설정 파일을 중심으로 각각 14개의 동일 파일을 기본 배포합니다.
    

이러한 공통 템플릿 제공은 사용자의 편의성을 높이는 훌륭한 기능이지만, **'AI가 프롬프트를 분석해 순수하게 작성한 로직'의 양을 측정해야 하는 채점 시스템에서는 코드량이 과대평가되는 변수**로 작용하게 되었습니다.

## 2. 해결책 1: 순수 로직(Pure Code) 추출 필터링 도입

위와 같은 산업 전반의 생성 트렌드를 반영하여, 평가의 객관성을 확보하기 위해 백엔드 시스템에 정밀한 **필터링 로직**을 새롭게 도입했습니다.

- `package-lock.json`, `bun.lockb`, 린트(Lint) 설정, 컴파일 옵션 등 인프라 구성을 위한 설정 파일들을 글자 수 계산에서 배제합니다.
    
- 전체 용량에 큰 영향을 미치는 범용 UI 라이브러리(`components/ui/` 등) 및 빌드 산출물 폴더를 제외합니다.
    

결과적으로 시스템은 공통 템플릿을 걷어내고, AI가 당면한 과제 해결을 위해 직접 작성한 **'순수 비즈니스 로직(Pure Code)'**만을 추출하여 측정 모수로 활용하게 되었습니다.

## 3. 해결책 2: 최신 Gen Efficiency (v1.1) 평가 공식 적용

추출된 `순수 코드 길이`와 `초 단위 소요 시간`을 바탕으로, 단순 속도 측정을 넘어 난이도와 밀도를 종합적으로 고려하는 3단계 수학적 연산을 적용합니다.

### 1단계: 복잡도 ($C$) 산출 및 상한(Cap) 적용

각 과제의 난이도에 맞는 적정 코드량 기준을 설정하여, 불필요하게 코드가 길어지는 것을 효율성 지표에서 제어합니다.

$$C = \frac{\min(\text{Pure Code Length}, \text{Cap})}{10,000}$$

- **L1 (단순 랜딩):** 최대 25,000자 인정
    
- **L2 (App/CRUD):** 최대 80,000자 인정
    
- **L3 (Service/E2E):** 최대 150,000자 인정
    

### 2단계: 난이도 보정 효율 ($E$) 계산

산출된 복잡도($C$)에 난이도별 가중치($W$)를 곱한 뒤, 생성 소요 시간(초)으로 나누어 초당 실질 생산성 지표($E$)를 구합니다. 결제/인증 등 복잡한 워크플로우를 구현하는 과제일수록 높은 가중치가 부여됩니다.

$$E = \frac{C \times W}{\text{Generation Time (seconds)}}$$

- **난이도 가중치 ($W$):** L1 = **1.0** / L2 = **1.8** / L3 = **2.5**
    

### 3단계: 절대 평가 점수 맵핑 (Threshold)

계산된 효율성 지표($E$)를 **L1, L2, L3 난이도별로 세분화된 커트라인**에 대입하여 최종 점수를 확정합니다. 특히 L3는 구현 난이도가 높으므로 고득점을 위해 더 엄격한 기준을 적용하여 변별력을 높였습니다.

|**점수**|**L1 컷 (완화)**|**L2 컷 (기본)**|**L3 컷 (엄격/분리)**|
|---|---|---|---|
|**5.0점**|$E \ge 0.0080$|$E \ge 0.055$|$E \ge 0.070$|
|**4.0점**|$E \ge 0.0060$|$E \ge 0.040$|$E \ge 0.050$|
|**3.0점**|$E \ge 0.0045$|$E \ge 0.030$|$E \ge 0.038$|
|**2.0점**|$E \ge 0.0035$|$E \ge 0.020$|$E \ge 0.026$|
|**1.0점**|$E < 0.0035$|$E < 0.020$|$E < 0.026$|

## 4. 품질 보증을 위한 안전장치 (Guardrails)

계산식에 따라 5.0점 만점이 도출되더라도, 생성된 결과물의 실제 동작 품질에 문제가 있다면 점수를 제한하는 상한선(Penalty Cap)을 적용하여 신뢰도를 유지합니다.

1. **핵심 기능 실패 상한 (Max 3.0점):** 코드가 빠르게 생성되었어도, 앱 빌드가 실패하거나 요구된 핵심 플로우가 작동하지 않으면 최대 3.0점으로 제한합니다.
    
2. **얕은 구현 상한 (Max 4.0점):** 실제 작동하는 앱의 화면 깊이(E2EDepth)가 과제 난이도에 미치지 못하는 경우 (예: L3 과제임에도 3단계 이하로 워크플로우가 종료되는 경우) 최대 4.0점까지만 인정합니다.
