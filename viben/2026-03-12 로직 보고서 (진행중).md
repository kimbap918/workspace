## 무엇을 평가하는가: 난이도 및 채점 항목


<br>

### 1. 프롬프트 난이도 레벨 (PDL)


평가 전, 입력된 프롬프트를 L1, L2, L3로 분류하여 채점의 기준점(Anchor)을 다르게 적용, PDL은 **A-4 Logic**, **B-1 CodeQuality**, **B-2 GenEfficiency** 평가 기준에 반영.

- **L1 — Landing/소개형**
    
    - 키워드 예: introduce, showcase, landing, portfolio, just introduce
        
    - 섹션 구성/내비/탭·필터/제품 상세(모달·섹션) 중심 소개 경험을 기대함. (목표 E2EDepth: 1)
        
- **L2 — App/CRUD형**
    
    - 키워드 예: dashboard, admin, CRUD, save/edit/delete, database, API, search+filter+sort
        
    - 데이터 생성·수정·삭제, 폼 검증, 상태관리, 에러 처리를 기대함. (목표 E2EDepth: 2)
        
- **L3 — Service/E2E형**
    
    - 키워드 예: auth/login, role/permission, payment/checkout, booking, subscription, onboarding
        
    - 인증·권한·결제/완료 상태 포함 다단계 워크플로우를 기대함. (목표 E2EDepth: 4)
        

<br>

### 2. 3대 평가 섹터

#### A. Core Performance (핵심 성능 - 60%)

> **목적:** 사용자의 의도를 단순 코드가 아닌 "시장 출시가 가능한 프로덕트"로 구현하는 능력을 평가

$$A_w = 0.15\text{Context} + 0.10\text{Multimodal} + 0.15\text{Localization} + 0.20\text{Logic} + 0.20\text{Layout} + 0.20\text{Depth}$$

#### B. Developer Experience (개발 및 운영 효율 - 30%)

> **목적:** 깊이 연동형 생성 속도 보정, 운영 효율, 비용 대비 산출물 완성도를 평가

$$B_w = 0.40\text{Quality} + 0.40\text{Efficiency} + 0.12\text{Cost} + 0.08\text{SelfHealing}$$

#### C. Brand Readiness (브랜드 준비도 - 10%)

> **목적:** 일관된 디자인 시스템과 브랜드 아이덴티티를 갖췄는지 평가

$$C_w = 0.40\text{Identity} + 0.35\text{Consistency} + 0.25\text{Assets}$$

## 어떻게 계산하는가: 채점 방식

### 1. 앵커(Anchor) 시스템

모든 세부 항목은 1점(Critical Failure)부터 5점(Strict Perfect)까지의 기준표에 따라 채점.

> **Note:** Evidence(증거)가 없으면 점수는 인정되지 않음. 증거 확보가 불가능한 경우 보수적으로 채점하거나 '미확인' 처리

### 2. 총점 산정식

$$\text{Total Score} = (A_w \times 12) + (B_w \times 6) + (C_w \times 2)$$

- $A_w$: 핵심 성능(Core Performance, 60%) 가중평균 (1~5)
    
- $B_w$: 개발 효율(Developer Experience & Efficiency, 30%) 가중평균 (1~5)
    
- $C_w$: 브랜드(Brand Readiness, 10%) 가중평균 (1~5)
    

<br>

### 3. 채점 방식 (5단계 파이프라인)

- **입력:** 평가 근거는 실시간 Live URL, 프로젝트 루트의 Code ZIP, 스크린샷 그리고 생성 시간으로만 제한
    
- **증거:** 모든 세부 점수는 파일 경로, 특정 화면 섹션 등 최소 2개 이상의 명확한 증거가 있어야만 인정
    
- **추론:** 코드, 스크린샷의 일부가 누락되었더라도, 폴더 구조나 import 구문 등 명백한 시그널이 있다면 이를 바탕으로 기능을 추론
    
- **분석:** System Prompt와 스코어링 기준을 탑재한 Gemini 모델이 라우팅 구조 및 상태 흐름 분석, 수식 계산을 스스로 하지 않고, 증거 기반의 원점수(Raw Score) 채점표만 JSON 형태로 생성
    
- **반복:** AI의 환각을 막기 위해 동일 조건에서 N회 채점을 진행하며, 최고/최저점을 제외한 평균(10% Trimmed Mean)을 최종 반영
    

<br>

### 4. 채점 안정화 메커니즘 (우선순위)

채점 과정에서는 극단값과 환각을 막기 위해 두 가지 안정화 메커니즘이 순차적으로 적용.

**1순위 — Verification Gate (실행 실패 제한)**

실행 실패 또는 런타임 오류 발생 시 주요 항목에 강력한 상한선(Cap)을 먼저 씌움. 해당 문제는 확정적 부정 증거이므로 최우선 적용.

|실패 유형|적용 항목|Cap 수치|
|---|---|---|
|로드 실패 / HTTP 4xx~5xx|Logic, StandardLayout, E2EDepth|**2.0**|
|로드 실패 / HTTP 4xx~5xx|UIConsistency|**2.5**|
|런타임 에러 (console/page error)|Logic|**3.0**|
|런타임 에러 (console/page error)|SelfHealing|**3.0**|

<br>


**2순위 — Score Shrinkage (증거 부족 보정)**

Verification Gate 적용 이후에도 코드베이스가 작거나 증거량이 부족하여 4~5점이 남발되는 것을 막기 위해, 베이지안 평균(Bayesian Average)을 활용해 점수를 기본 3.0 근처로 수축.

$$Score_{shrunk} = \frac{E \times Score_{raw} + k \times 3.0}{E + k}$$

- $E$ (Evidence Strength): 순수 코드 길이, 유효 파일 수, 발췌본 수 등을 로그 스케일로 환산하여 합산한 유효 증거량
    
- $k$ (Prior Strength): 수축 강도를 결정하는 사전 가중치 (기본값: 8.0)
    
- $Score_{raw}$: 모델이 증거를 기반으로 채점한 원점수
    

> **면제 조건:** 채점 과정에서 5점 조건을 충족하는 명확한 완벽 증거(`is_perfect_evidence_found = True`)가 확인된 항목은 수축 패널티에서 전면 면제됩니다.

## 항목별 상세 평가 기준

<br>


### Ⅰ. A. 핵심 성능 표준 (Core Performance - Weight 0.60)

#### i. 주요 평가 항목 보충 정의 (Clarifications)

- **Context (의도 파악):** 프롬프트 의도를 실제 UX 구조로 해석하는 능력을 의미 (예: "Tesla Cybertruck showcase" 요청 시 단순 텍스트 나열이 아닌 Hero, Specs, Gallery, CTA 등으로 구조화했는지 평가)
    
- **Multimodal (이미지 생성):** 단순 코드 생성이 아닌 외부 시각 자산 통합 능력을 평가. 단순 placeholder 이미지는 가점이 되지 않으며, 아래 중 하나 이상의 명확한 증거가 필요.
    
    - 외부 이미지 URL 직접 사용 (Unsplash, Pexels, Cloudinary 등)
        
    - 아이콘 라이브러리 통합 (lucide-react, react-icons, @heroicons 등)
        
    - 차트 라이브러리 (recharts, d3, chart.js 등)
        
    - 지도/영상/3D 컴포넌트 (mapbox, leaflet, Three.js 등)
        
    - asset manifest / media metadata 파일 존재
        
    - 인라인 SVG 사용
        
- **Localization (로컬 언어 최적화):** 단순 기계 번역이 아닌 '현지화 경험(Local UX)'을 의미, 타겟 언어 일치뿐만 아니라 현지 통화 표시(₩ 등), 날짜 포맷(2025년 3월 21일), 어색함 없는 UX Writing을 복합적으로 평가.
    
<br>

#### ii. Logic (기능 완결성) 체크리스트

- **L1:** UI 인터랙션(필터, 탭)과 빈 상태(Empty State) 구현 여부를 확인함.
    
- **L2:** L1 + CRUD 기능 작동 여부와 폼 에러 처리 여부를 확인함.
    
- **L3:** L2 + 인증, 결제 프로세스 완결성(과정, 실제 결제가 되는것을 판단하지 않음)과 엣지 케이스(예외 상황) 방어 로직 존재 여부를 확인함.
    

<br>

### Ⅱ. B. 개발 및 운영 효율 (Developer Experience - Weight 0.30)

#### i. Code Quality (코드 품질) 기대치

- **L1:** 컴포넌트 분리와 스타일 시스템 준수 여부를 확인함. 백엔드 로직 부재는 감점 요인이 아님.
    
- **L2:** L1 + 데이터 레이어 분리(Hooks/API) 등을 확인함.
    
- **L3:** L2 + 보안 가드(Auth Guard), 민감 정보 처리, 예외처리 설계 여부를 확인함.
    

<br>

#### ii. 생성 효율 (GenEfficiency) 평가식 (Fair Version)

백엔드 서버에서 추출된 데이터를 바탕으로, 단순히 코드를 길게 작성하는 꼼수를 막고 생성에 걸린 시간 패널티를 완화하여 "핵심 기능이 포함된 실질적인 밀도"를 평가하도록 백엔드 연산을 수행.

**Step 1. 유효 산출물 단위 (Effective Units) 계산 및 난이도 보정**

$$EU = (L_{code} \times 0.35) + (C_{file} \times 250) + (C_{excerpt} \times 180)$$

$$EU_{adjusted} = EU \times PDL_{multiplier}$$

- $L_{code}$ (Pure Code Length): ZIP에서 추출된 순수 소스 코드의 문자 수(character count). `node_modules`, `dist`, 자동 생성 UI(`components/ui`) 등은 철저히 배제.
    
- $C_{file}$ (File Count): $L_{code}$ 연산에 포함된 유효 코드 파일 수. 80 characters 미만의 파일, 단순 re-export index, 아이콘/스타일 전용 파일 등은 제외.
    
- $C_{excerpt}$ (Excerpt Count): LLM 분석을 위해 ZIP에서 추출된 핵심 코드 조각 수. `routes` → `api` → `state` 우선순위로 추출된 유효 컨텍스트 양.
    
- $PDL_{multiplier}$: 과제 난이도별 가중치 (L1=1.0, L2=1.2, L3=1.35)

<br>


**Step 2. 시간 패널티 완화 및 기초 효율 (Base Efficiency) 산출**

$$TP = \sqrt{\max(T_{sec}, 1)}$$

$$BaseEff = \frac{EU_{adjusted}}{TP}$$

- $T_{sec}$ (Generation Time): 프롬프트 입력 시점부터 코드 생성이 완료될 때까지 걸린 시간(초). 복잡한 로직을 구현하느라 시간이 걸린 모델을 구제하기 위해 선형 비례가 아닌 제곱근(Square Root)으로 시간 패널티($TP$)를 완화.
    

> **⚠️ 생성 시간 미입력 시 주의:** $T_{sec} = 0$이면 $\max(T_{sec}, 1)$로 처리하는 것이 아니라, GenEfficiency 점수가 1점으로 강제 설정됩니다. 반드시 생성 시간을 입력해야 정상 산출됩니다.


<br>

**Step 3. 품질 가중치 (Quality Multiplier) 반영 및 최종 산출**

$$QM = 0.80 + (0.06 \times Score_{Logic}) + (0.04 \times Score_{Depth})$$

$$FinalEff = BaseEff \times QM$$

- $QM$ (Quality Multiplier): 코드 밀도와 설계 완성도를 반영하는 보정 계수. 코드가 길어도 동작하지 않으면(낮은 Logic/Depth) 효율 점수가 깎이고, 짧아도 구조가 훌륭하면 부스트를 받아 단순 생산량 경쟁으로 변질되는 것을 방지.


<br>

**Step 4. 절대 평가 점수 맵핑**

|**최종 점수**|**L1 커트라인**|**L2 커트라인**|**L3 커트라인**|
|---|---|---|---|
|**5.0점**|FinalEff ≥ 2200|FinalEff ≥ 3200|FinalEff ≥ 4200|
|**4.0점**|FinalEff ≥ 1500|FinalEff ≥ 2400|FinalEff ≥ 3200|
|**3.0점**|FinalEff ≥ 900|FinalEff ≥ 1500|FinalEff ≥ 2100|
|**2.0점**|FinalEff ≥ 500|FinalEff ≥ 900|FinalEff ≥ 1300|
|**1.0점**|FinalEff < 500|FinalEff < 900|FinalEff < 1300|
